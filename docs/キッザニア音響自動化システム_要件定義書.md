# キッザニア館内音響自動化システム 要件定義書

作成日: 2026年7月25日
バージョン: v0.1(ドラフト)

---

## 1. プロジェクト概要

現在Windowsタスクスケジューラーで個別に実行している館内音楽・ステージ演出の
再生を、単一のPythonアプリケーションに統合する。朝に一度起動しておけば、
以降は無人でスケジュール通りに音楽が自動再生され、ステージショーはZV
(スタッフ)がボタン操作で手動トリガーできる状態を目指す。

## 2. 現状の課題

- タスクスケジューラーで個別に音楽ファイルを起動しているため、音源ごとの
  音量差を都度手動調整する必要がある
- 複数のプレイヤー/プロセスがバラバラに常駐し、管理が煩雑
- ステージ演出はPowerPointで動画・音楽を再生しており、同期が不安定になりやすい

## 3. 機能要件

### 3.1 自動音楽再生機能(スケジュール実行)

- 指定時刻に指定した音源ファイルを自動再生する(館内BGM等)
- 毎時1回、街時計ダンス用の音楽を自動再生する
  - 再生中は館内BGM(別端末・別システムで再生中)が自動的に小さくなる
    (ハード側のダッキング処理と推定。詳細は「7. 未確定事項」参照)
  - 再生終了後は特に操作せずとも館内BGMの音量が自動的に戻る想定
- スケジュールはcron形式で管理し、担当者が時刻・音源を編集できること
  (例: `APScheduler`によるジョブ管理)
- 音源ごとに個別の再生音量を設定・保持できること
  (旧タスクスケジューラー方式の課題を解消)

### 3.2 ステージショー手動再生機能

- ZV(スーパーバイザー以下スタッフ)がPythonシステムのGUI上の
  スタートボタンを押すと、対応する動画ファイル(ダンスショー/
  ファッションショー、音楽・映像入り)をフルスクリーンで再生する
- 現行PowerPointでの運用を廃止し、動画ファイル+専用プレイヤーに置き換える
  (音声・映像の同期問題を解消するため)
- 再生はPC→HDMI出力→音響映像システム→スクリーンの経路
- **前提条件**: 動画再生前に、音響映像スタッフが操作盤で入力を
  「イベント卓」に手動切替していること(本システムの制御範囲外。
  詳細は「6. 運用フロー」参照)

### 3.3 音量管理機能

- 音源(館内BGM/街時計/ステージ動画など)ごとに個別音量設定を保持
- GUIまたは設定ファイルで音量を調整・保存できること

### 3.4 映像出力機能

- 動画ファイルをフルスクリーンでHDMI出力できること
- 音声・映像のズレが生じないこと

## 4. 非機能要件

- ローカル音源ファイルのみで動作すること(オフライン動作可能。
  将来的にネット経由の音源配信を追加する余地は残す)
- 常駐プロセスは1つのみとし、朝1回の起動で以降は無人運用できること
- 再生失敗時(ファイル破損・出力デバイス切断等)にアプリ全体が
  停止しないこと、ログに記録されること
- 誰が触っても安全な最小限のGUI(誤操作防止)であること

## 5. システム構成(現時点の想定)

| 要素 | 想定技術 |
|---|---|
| スケジュール管理 | Python + APScheduler |
| 音声・動画再生 | python-vlc(VLCエンジン) |
| 手動トリガーGUI | Tkinter または PyQt |
| 音量管理 | アプリ内設定(JSON等)で音源ごとに保持 |
| 実行環境 | Windows常駐(会社PC、HDMI出力) |

## 6. 運用フロー(現状把握分)

1. 朝、担当者がPythonアプリを起動(以降は無人でスケジュール実行)
2. 通常時間帯: 館内BGMを別端末が再生中
3. 毎時: 本システムが街時計音楽を自動再生 → 館内BGM側が自動的に
   ダッキング → 再生終了後、館内BGM音量が自動的に復帰
4. ステージショー実施時:
   a. 音響映像スタッフが操作盤で「イベント卓」入力に手動切替
   b. ZVが本システムのスタートボタンを押す
   c. 動画がフルスクリーン再生(音声・映像同期)

## 7. 制約事項・外部依存

- 映像入力の切替(イベント卓)は音響映像スタッフの手動操作であり、
  本システムから自動制御はしない(現状、切替機材がAPI制御に
  対応しているか未確認のため)
- 館内BGMのダッキングは別システム(ハード側)の自動処理に依存し、
  本システムからの明示的な音量制御コマンドは想定しない
  (要検証。7.1参照)

## 8. 未確定事項・要確認事項

- [ ] 館内BGMのダッキングは本当に完全自動(音声信号検知)か。
      それとも街時計/ステージ動画の再生と連動した何らかの
      制御信号が必要か
- [ ] ステージショー開始時、「イベント卓に切替済みか」を
      ZVが目視確認する運用のままでよいか、システム側に
      確認ステップ(チェックボタン等)を入れるか
- [ ] 音源・動画ファイルの命名規則、保存フォルダ構成
- [ ] 具体的なスケジュール一覧(何時に何を再生するか、
      館内BGMの種類は何パターンあるか)
- [ ] 再生中にPCがスリープ/スクリーンセーバーに入らないための
      電源設定の確認
- [ ] 音響映像システム(切替機材)の型番・API対応有無の確認
      (将来的な自動化余地の判断材料として)
- [x] ステージ照明との連動について。**解決済み(2026年7月30日)**。実機は
      Zero 88 FLX S24(ZerOS)で、OSC(UDP)による外部トリガーに対応して
      いることを確認。本アプリに実装済み(詳細は「9. 追加改善」参照)。
- [ ] 「タブレットタッチで音楽・映像・照明が動く」仕組みの遠隔操作について。
      調査の結果、これは本アプリ(kidzania_sound)ではなく、音響映像業者が
      別途構築した本リポジトリ外のシステムと判明した。ソース・仕様とも不明
      のため今回は実装対象外。遠隔操作を実現するには以下を現地・業者側に
      確認する必要がある:
      - そのシステムの製品名・ソフトウェア/ハードウェア構成(タブレット上で
        動くアプリなのか、専用ハード(AVプロセッサ等)がタブレットのタッチを
        トリガーとして受けているだけなのか)
      - ネットワークAPI・シリアル(RS232)・外部入力等、遠隔操作可能な
        インターフェースを持つか
      - 業者への改修依頼が可能か、その場合の費用・納期
      - (運用担当者の見立て)Miracast等のワイヤレスディスプレイとして
        認識している可能性がある。該当する場合、Windowsの「接続」アプリ/
        ワイヤレスディスプレイへのプロジェクション機能や、AV側のワイヤレス
        レシーバー機器(型番)を確認すると仕組みの手がかりになる。

## 9. 2026年7月時点での追加改善(実装済み)

以下は運用担当者からの追加要望を受けて実装した機能。実装にあたっての
仕様上の判断を記録しておく。

- **スケジュールの柔軟化**: GUIの「スケジュール管理」画面で、頻度に
  「時間帯」を選べるようになった(例: 10時〜18時は毎時00分に再生。
  18時以降・10時より前は再生しない)。また
  「休止時間帯」タブで、指定時間帯は全ジョブの再生を止められるように
  なった(例: 12時〜13時は再生しない)。時間帯指定は日をまたぐ範囲
  (例: 22時〜翌2時)を1行では表現できない仕様とした(APSchedulerのcron
  範囲構文の制約のため)。日をまたぐ場合は「22時〜23時」「0時〜2時」の
  ように2行に分けて登録する。休止時間帯側は自前のdatetime比較で判定して
  いるため日またぎにも対応している。
  - 各休止時間帯には適用する営業モード(通し営業/2部制営業/共通)を
    選べるようにした。「共通」を選ぶと営業モードによらず常に適用される
    (クローズ後、当日どちらのモードで開けていても誤作動しないようにする
    用途を想定)。モード切替時に該当する休止時間帯だけが再読み込みされる
  - メイン画面の「次の予定」パネルで、休止時間帯に該当し実際には
    再生されない回は一覧から非表示にした(その回のnext_run_timeが
    休止時間帯を抜けるまで表示されない。表示件数は非表示分を除いた
    実際に再生される予定の件数で数える)
  - スケジュール管理画面の各行に▲▼ボタンを追加し、見やすさのための
    表示順の並び替えができるようにした(時刻順に並べ直す等)。並び替えは
    表示順(=保存されるJSON内の並び順)のみを変更し、各ジョブに設定した
    時刻・cron自体は一切変更しない
- **2台のSurface連携**: `config/settings.json`の`link`セクションで
  `enabled: true`にすると、2台のSurface(1台=スケジュール自動再生担当、
  1台=ステージショー手動操作担当を想定)を連携できる。同期される内容:
  - スケジュール/ステージショー/休止時間帯の設定(片方で保存すると
    もう片方にも反映される。同時編集は考慮しておらず、後から保存した方が
    勝つ(last-write-wins)。取りこぼし対策として30秒間隔(設定可)で
    差分をポーリングし自動的に追いつく)
  - 再生状態の連動: 片方で再生が始まると、もう片方の再生中音量が
    `duck_volume_percent`(既定20)の割合まで一時的に下がり、終了すると
    元に戻る(複数が同時に再生中でも、全て終わるまでは音量を戻さない
    参照カウント方式)
  - 一括停止・営業モード切替: 片方の「■停止」やモード切替はもう片方にも
    伝播する。「■停止」は**もう片方の再生中の全て(ステージ動画・
    スケジュールBGM双方)を停止する**仕様とした(運用担当者確認済み)
  - 施設内の閉域LAN・端末2台限定を前提とし、認証機構は入れていない
    (送信元IPの簡易フィルタのみ)。この前提が崩れる場合(LANが外部と
    繋がっている等)は要再検討。
- **システム設定画面**: GUI右上の「システム設定...」ボタンから、
  `config/settings.json`を手編集せずに以下を変更できるようになった:
  - この端末の名前(device_name)。ウィンドウタイトルやサブヘッダーに
    表示され、連携先への通知にも付与される(将来3台以上に拡張した際の
    送信元識別に備えた設計)
  - リンク機能の有効/無効、相手端末のIP・ポート、自機の待受ポート、
    ダッキング音量、監視間隔
  - 相手端末のIP/ポート・ダッキング音量・監視間隔は保存後すぐに反映される。
    リンク機能の有効/無効・待受ポート番号の変更のみアプリの再起動が必要
    (稼働中のHTTPサーバーの起動・停止を伴うため)
  - 監視間隔の既定値は当初60秒(1分おき)としていたが、常時監視したいという
    要望により後述の10章で1秒に変更した。この間隔で接続状態
    (「連携: 接続中(相手端末名)」/「連携: 未接続」)がサブヘッダーに
    表示され続ける
- **照明卓(Zero 88 FLX S24)との連動**: 実機確認済みの仕様に基づき、
  `src/kidzania_sound/lighting.py`でOSC(UDP)送信を実装した(`python-osc`を
  新規依存として追加)。
  - 送信先・コマンド書式(変更不可の実機仕様): `192.168.1.10:8830`(UDP)へ
    `/zeros/playback/go/<プレイバック番号>`
  - `config/settings.json`の`lighting`セクション(`enabled`/`host`/`port`)で
    有効化。`enabled: false`が既定で、照明卓未接続の開発機でも安全
  - `schedule.json`の`lighting_cues`で「フェアウェル」「ファッションショー」
    「FUNFUN/フィナーレ/ステージダンスショー」「ウェルカムダンス」の
    4つの名前付きキュー(→プレイバック番号)を定義済み。各キューは
    複数のプレイバック番号を持てる(例: FUNFUN系は37と42の両方に送信)
  - スケジュールジョブ・ステージショーそれぞれに、GUIの「スケジュール
    管理」画面(ドロップダウン)から照明キューを紐付けられる。キューの
    追加・編集自体は新設の「照明キュー」タブで行う
  - **重要な運用制約**: 音響PC(スケジュール担当機・ステージショー担当機の
    両方とも、それぞれが照明キューを送信する可能性があるため)は照明卓と
    同一LANセグメント(192.168.1.x/24、ゲートウェイなし)に、192.168.1.10と
    重複しない固定IPで接続する必要がある。2台のSurface連携機能の
    `peer_host`/`peer_port`もこのセグメント内で到達可能である必要があり、
    現地のネットワーク構成(1つのセグメントに全端末を収容できるか、
    スイッチ増設が必要か)を確認すること
- **実メディアファイルの反映**: `Downloads\Kidzania\`にあった実際の音源・
  動画ファイルを`media/`に配置し、`schedule.json`/`stage_shows.json`の
  参照をプレースホルダーから実ファイルに差し替えた。100MBを超える動画
  ファイル(GitHubの1ファイル上限)は`.gitignore`に追加し、git管理対象外と
  した(既存の`kidzania_Wrap up Party_loop_b2.wav`と同じ扱い)。
- **起動時のファイル存在チェック**: `schedule.json`/`stage_shows.json`が
  参照する全ての音源・動画ファイル(選択中の営業モードに限らず全モード
  対象)について、起動時にまとめて存在確認を行うようにした。見つからない
  ものがあってもアプリの起動は継続し(無人運用を止めないため)、ログへの
  記録と起動直後の警告ダイアログで運用担当者に知らせる。
- **動画(クリップ)ごとの照明キュー**: `StageShow`を「clips」単位(動画ファイル+
  クリップごとの照明キュー)に再構成した。ファッションショーのように1つの
  ショーが複数動画で構成される場合、動画(演出)ごとに異なる照明キューを
  割り当てられる。「次のMV ▶」ボタンで動画を切り替えるたびに、その動画に
  紐付いた照明キューが送信される。既存データ(ショー単位の単一キュー)は
  自動的に全クリップへ引き継がれ、次回保存時に新形式へ移行する。
- **時間帯スケジュールの分単位指定**: 「時間帯」頻度の開始・終了を、時単位
  だけでなく分単位まで指定できるようにした(例: 9時35分〜18時20分の間、
  毎時00分に再生)。内部的には毎時◯分のcronで発火させたうえで、発火時に
  分単位の時間帯内かどうかを判定して再生要否を決める方式(休止時間帯と
  同じ仕組みを共通化)。既存の時単位のみのデータ(例: 10-13時)は分0扱いと
  して引き続き読み込める。
- **ステージショーのボタンレイアウト(メイン画面に統合)**: 当初は
  ラップアップパーティー・ファッションショーだけ専用の別ウィンドウ
  (`StageDetailWindow`)に分離していたが、運用担当者の要望により
  この別ウィンドウは廃止し、全ショーをメイン画面(ホーム)に統合した。
  - ショーごとに`ttk.LabelFrame`で囲み、ショー名を枠のタイトルとして
    表示する(ボタン内に長いタイトルを詰め込むと文字切れするため、
    タイトルはボタンの外に出した)
  - 単一動画のショー(fanfanバースデー・フェアウェル・ラップアップ
    パーティー): 枠の中に大きな正方形の「▶ 再生」「■ 停止」ボタンを配置
  - 複数動画のショー(ファッションショー): 枠の中に、設定済みの動画
    (クリップ)ごとに大きな正方形ボタンを配置し、押すとその動画へ直接
    切り替わる(順送りではなく直接選択)。専用の停止ボタンもあり
  - ボタンは全体的に大きく押しやすいサイズにしてあり、状況に応じて
    有効/無効・再生中クリップの見た目(凹み)が切り替わる
  - 画面下部の「■ すべて停止(緊急)」ボタンは、個別の停止ボタンとは
    別に、状況を問わず全ての再生を止める緊急停止として残している
  - **安全対策**: 「■ すべて停止(緊急)」(2台連携時は連携先からの
    一括停止要求も含む)は再生中の動画を止めるだけで、待機黒画面や
    「ステージショーモード」自体は解除しない。解除してしまうと拡張
    ディスプレイ(ゲスト側モニター)にWindowsのデスクトップが露出して
    しまうため、誤って画面が切り替わらないようこの仕様にしている。
    待機黒画面右下にあった「ESCキーで停止/待機画面を閉じます」という
    案内文言も、ゲスト側モニターに映ってしまうため削除した(ESCキー
    自体の操作は引き続き有効)
  - 映像プレビューは検討したが付けない方針とした
- **テストモード(手動再生・音量確認)**: メイン画面右上に「テストモード...」
  ボタンを追加し、押すと専用ウィンドウ(`TestModeWindow`)が開く。
  スケジュール/ステージショーの設定とは無関係な、その場限りの単発再生機能。
  - 音源ファイルはその都度「参照...」で自由に選択(あらかじめ登録された
    ジョブ/ショーである必要はない)
  - 再生タイミングは「今すぐ再生」(即時開始)または「カウントダウンで
    ○○秒後に再生」から選択
  - 再生中は音量スライダーがリアルタイムに反映される(`AudioCue.set_volume()`
    を新設)。用途は主に(1)緊急時の手動再生、(2)スケジュール登録前に
    音量を試聴しながら決め、その数値を「スケジュール管理」画面へ
    転記するための確認用。ここで調整した音量が自動でスケジュールに
    反映されるわけではない点に注意
  - 再生開始/終了は他の再生経路と同様にリンク機能へ通知され、連携先の
    ダッキングも動作する
- **ステージショー待機画面の背景画像**: 従来は黒一色だった待機画面
  (拡張ディスプレイ=ゲスト側モニターの待機表示)に、画像を設定できる
  ようにした(`Pillow`を新規依存として追加)。
  - `config/settings.json`の`standby_background_image`(media_root相対パス、
    空文字なら黒背景)で設定し、GUIの「システム設定」画面からも
    「画像を選択...」「黒背景に戻す」ボタンで変更できる
  - 選択した画像は、待機画面を表示する拡張ディスプレイの解像度に合わせて
    自動的にリサイズ(縦横比を保たない単純な引き伸ばし)して表示する
  - 変更は次に「ステージショーモード」をONにしたときから反映される
    (既に表示中の待機画面には即時反映されない)
  - 動画再生中はVLCの映像がこの背景画像の上に重なって表示される
    (待機画面と同じウィンドウを流用しているため)

## 10. 2026年8月時点での追加改善(実装済み)

運用担当者からの安全対策・利便性向上の要望を受けて実装した機能。

- **スケジュール再生中のリアルタイム音量調整**: メイン画面の「現在再生中」
  パネルに、再生中ジョブ1件ごとの音量スライダー(0〜100%)を追加した。
  不具合等で想定外の大音量になった場合に、その場で即座に絞れるようにする
  安全対策。`JobScheduler.set_active_volume()`/`get_active_volume()`を新設し、
  既存の`AudioCue.set_volume()`(テストモードで使用していたもの)を再利用
  している。パネルは1秒おきに再描画されるが、スライダーをドラッグ中に
  行ごと消えてしまわないよう、表示中のジョブはウィジェットを使い回す
  差分更新方式に変更した(終了したジョブの行のみ削除、新規開始分のみ追加)。
- **起動時の他アプリ音声ミュート**: HDMI経由で会場スピーカーに直結して
  いる運用のため、他アプリ(通知音・システムサウンド含む)の音が
  紛れ込むと現場事故になりかねない。そのため起動時に一度だけ、自プロセス
  以外の全音声セッションをミュートするようにした(`pycaw`を新規依存として
  追加、`src/kidzania_sound/system_audio.py`)。
  - `config/settings.json`の`mute_other_audio_on_startup`(既定`true`)で
    無効化も可能(トラブル時の切り分け用)
  - 対象はプロセス単位の音声セッション全て(システムサウンドを含む)。
    自アプリ自身の音声セッション(PIDが一致するもの)のみ除外する
  - 起動時の一回限りの処理であり、起動後に他アプリが新たに音を鳴らし
    始めた場合の継続的な監視・再ミュートは行わない(必要になった場合は
    別途要望として検討する)
  - `pycaw`が利用できない環境(Windows以外・ライブラリ未導入)では
    警告ログのみでスキップし、アプリ本体の起動は継続する
- **次回スキップの確認ダイアログ・取消**: 「次の予定」パネルの
  「次回スキップ」ボタンを押すと、誤操作防止のため
  「HH:MM の [ジョブ名] をスキップしますか？」という確認ダイアログを
  表示し、OKを押した場合のみスキップするようにした。
  - スキップ済みのジョブは「次の予定」パネルから消さず、
    「[スキップ済み]」の表示付きでそのまま残し、ボタンが
    「スキップ取消」に切り替わる(押すとスキップを取り消せる)。
    `JobScheduler.is_skipped()`/`cancel_skip()`を新設。
- **自端末IPアドレスの表示**: 「システム設定」画面の連携セクション上部に、
  この端末自身のLAN側IPアドレスを表示するようにした(`コピー`ボタンで
  クリップボードにコピーも可能)。もう1台のSurfaceの「相手端末の
  IPアドレス」欄への入力を、手打ちの手間・入力ミスなく行えるようにする
  ためのもの。取得には標準ライブラリの`socket`のみを使用し、実際の
  パケット送信は行わない(UDPソケットの`connect()`でルーティング表を
  引き、送信元IPを取得するだけの定番手法。`src/kidzania_sound/link.py`の
  `get_local_ip()`)。
- **連携の監視間隔を既定1秒に変更**: 「常に監視していたい」という要望を
  受け、`LinkConfig.poll_interval_seconds`の既定値を60秒から1秒に変更した
  (`config/settings.json`の現在値も1に更新済み)。あわせて、
  `link.py`のポーリングループに残っていた「最短5秒」のハードコードされた
  下限も1秒まで許容するよう修正した(このガードが残っていると、設定を
  1秒にしても実際には5秒間隔にクランプされてしまうため)。GUIの
  「システム設定」画面の監視間隔スピンボックスも下限を1に変更した。
  接続状態表示の判定しきい値(監視間隔の2倍)もこの値に連動して短くなり、
  より即応的に「連携: 接続中/未接続」が切り替わるようになる。
- **一日のタイムスケジュール一覧表示・出力**: 「スケジュール管理」画面は
  cron設定(◯時◯分・毎時◯分・時間帯)をそのまま編集する画面であり、
  「今日は結局何時に何が鳴るか」を一目で把握するには不向きだった。
  メイン画面に「一日の予定を表示...」ボタンを追加し、選択した営業モードの
  cronを実際に1日分展開したうえで、休止時間帯による無効化も反映した
  時刻順の一覧を表示する新しい画面(`DailyScheduleWindow`)を新設した
  (`src/kidzania_sound/schedule_report.py`に一覧構築ロジックを分離)。
  - 表示は画面を開いたときの営業モード選択が初期値だが、画面内の
    コンボボックスでいつでも別モードに切り替えて見られる
  - cronの実際の発火時刻はAPSchedulerの`CronTrigger.get_next_fire_time()`を
    1日分反復して求めており、独自のcron解釈ロジックは持たない(既存の
    スケジューラー本体と解釈がずれないようにするため)
  - 休止時間帯に該当し実際には再生されないジョブの発火は一覧から除外し
    (「次の予定」パネルと同じ考え方)、代わりに休止時間帯自体を
    「13:29〜13:59【休止時間帯】〇〇」のように1件のエントリとして表示する。
    深夜またぎの休止時間帯(例: CL後〜翌朝)は「20:05〜翌08:24」のように
    「翌」を付けて表示する
  - 無効化(enabled=false)されたジョブは一覧に出さない(実際に鳴らない
    ため)
  - 画面右上の「テキストファイルに保存...」ボタンで、同じ内容をテキスト
    ファイルに書き出せる(印刷用。ファイル名は既定で
    `タイムスケジュール_YYYYMMDD_モード名.txt`)
- **ショー単位のクリップ切替・終了時の黒背景**: ステージショー待機画面の
  背景画像(`standby_background_image`)は、動画再生中はVLCの映像で
  隠れるが、クリップ切り替え時(「次のMV」やファッションショーの個別
  クリップボタン)や動画終了直後の一瞬だけ背景画像が見えてしまう。
  ファッションショーのみ、この「一瞬見える」区間を背景画像ではなく
  黒背景にしたいという要望を受け、`StageShow`に
  `black_background_on_gap`(既定`false`)を追加した。
  - `true`のショーは、そのショーの再生を開始した時点から、クリップ切替
    ごと・そのショーの再生が終わって待機状態に戻った後も、次に別の
    ショーを再生するまでは黒背景のままになる(背景画像には自動的には
    戻らない。「終わったら黒背景に」という要望どおりの挙動)
  - 別のショー(このフラグがfalseのもの)を再生すると、通常通り
    設定された背景画像に戻る
  - 現状`stage_shows.json`の`fashion_show`のみ`true`に設定済み。
    「スケジュール管理」画面の「ステージショー」タブにも
    「クリップ切替・終了時は黒背景」チェックボックスを追加したので、
    今後どのショーに適用するかはGUIから変更できる
